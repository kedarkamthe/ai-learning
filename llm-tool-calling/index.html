Understanding AI Agents

Why Tool Calling Matters

LLMs are powerful, but limited to training data—which becomes outdated quickly. Tool calling is the mechanism that lets LLMs interact with real-world systems.

  • Without tools: Static knowledge, no real-time data access
  • With tools: Fetch current info, query databases, call APIs
  • Real impact: Your AI agent can now think AND act

Think of it like your doctor getting your lab results before diagnosing you. The LLM is the doctor. The tools are the lab tests.

The Critical Insight

LLM ≠ Agent

The Fundamental Distinction

LLM: Decides WHAT to do (returns instructions)

Agent: DOES the work (executes tools)

The LLM never touches your database. It never calls your API. It only decides that these things should happen. Your agent code makes them happen.

Flow: User Request → LLM decides → Agent executes → Results sent back → LLM processes

The Request/Response Cycle

5 Steps in Every Tool Call

Step 1: Agent → LLM (Request)
Send user request + system prompt + tool definitions to LLM
Step 2: LLM Response (Decision)
LLM returns "You should call fetch_diff with these parameters" (not the actual data)
Step 3: Agent Executes
Your code runs the tool, gets the actual result
Step 4: Agent → LLM (Results)
Send results + full history + system prompt AGAIN to LLM
Step 5: LLM Processes
LLM sees results and decides: final answer or call another tool?

⚠️ Critical: System prompt is sent with EVERY request (1 & 4). It's not cached.

Step 1: Initial Request

What Gets Sent to LLM

Request 1: Agent to LLM
{
  "model": "claude-opus-4-5",
  "system": "You are a code reviewer. Use available tools to analyze code changes.",
  "tools": [
    {
      "name": "fetch_mr_diff",
      "description": "Fetch the diff from a GitLab MR",
      "input_schema": {
        "type": "object",
        "properties": {
          "mr_id": {"type": "string"},
          "project_id": {"type": "string"}
        }
      }
    }
  ],
  "messages": [
    {
      "role": "user",
      "content": "Review GitLab MR #42 for security issues"
    }
  ]
}

Key: Everything LLM needs to make a decision is sent in this one request.

Step 2 & 3: LLM Decides + Agent Executes

The tool_use Block

LLM Response (Step 2)
{
  "content": [
    {
      "type": "text",
      "text": "I'll analyze this MR for security issues. Let me fetch the diff first."
    },
    {
      "type": "tool_use",
      "id": "tool_call_001",
      "name": "fetch_mr_diff",
      "input": {
        "mr_id": "42",
        "project_id": "red-hat-platform"
      }
    }
  ]
}

Important: LLM returns METADATA (what to call), not the actual result. Your agent executes the tool and gets the real data.

The id: "tool_call_001" is critical—it's how results will be matched to this decision.

Step 4: Agent Sends Results Back

Request 2: Full Context

Request 2: Agent to LLM (After Tool Execution)
{
  "model": "claude-opus-4-5",
  "system": "You are a code reviewer...",
  "tools": [...],
  "messages": [
    {"role": "user", "content": "Review GitLab MR #42..."},
    {
      "role": "assistant",
      "content": [
        {"type": "text", "text": "I'll analyze this MR..."},
        {"type": "tool_use", "id": "tool_call_001", "name": "fetch_mr_diff", "input": {...}}
      ]
    },
    {
      "role": "user",
      "content": [
        {
          "type": "tool_result",
          "tool_use_id": "tool_call_001",
          "content": "File: auth/login.py\n- Line 12: SQL injection risk\n- Line 45: Password stored as plaintext"
        }
      ]
    }
  ]
}

Critical: The tool_use_id must match the id from Step 2. This links the result to the decision.

The Linking Mechanism

Why ID Matching Is Critical

LLM Says (Step 2)

{
  "type": "tool_use",
  "id": "tool_call_001",
  "name": "fetch_mr_diff",
  "input": {...}
}

Agent Reports (Step 4)

{
  "type": "tool_result",
  "tool_use_id": "tool_call_001",
  "content": "File: auth/login.py\n- Line 12: SQL injection"
}

MUST MATCH! Without matching IDs, the LLM won't know which result corresponds to which tool call.

This is how LLM tracks multiple parallel tool calls correctly.

Optimization Patterns

Parallel vs Sequential

Parallel Calling

When: Tools are independent

Example: Fetch diff, commits, CI status—all at once

Request 1 → 3 tool_use blocks → Execute all 3 → Request 2 sends all 3 results

Benefit: 71% fewer requests = massive token savings

Sequential Calling

When: Tool B needs Tool A's output

Example: Get user_id → Fetch profile → Check permissions

LLM naturally recognizes dependency and returns only 1 tool_use per request

Automatic: No manual sequencing needed

Summary

Key Takeaways

  • LLM decides (returns metadata), Agent executes (runs tools)
  • System prompt + tools sent with EVERY request (not cached)
  • tool_use ID must match tool_result tool_use_id—this is the glue
  • Parallel calling saves 70%+ tokens on multi-tool workflows
  • LLM naturally sequences dependent tools intelligently
  • Each cycle = separate API request (not chained automatically)
